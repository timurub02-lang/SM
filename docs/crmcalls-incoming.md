# CRMCalls → Заказы → Новые

`POST /api/crmcalls-incoming` принимает `call.result_saved` для явно выбранных ID сценария и результата. Приём выключен до настройки администратором в разделе CRMCalls. Результат «СМ СРМ» создаёт стандартную карточку `draft` с пустой корзиной, без товаров, суммы, складских и финансовых операций. Оператор определяется только по явному соответствию `user.id` → ID активного оператора CRM. Совпадение имён не используется.

## Настройка

1. В CRMCalls → Интеграции → API → Документация проверьте актуальный контракт. Проверено 24.11.2026 по руководству `https://cc.crmcalls.ru/docs/crmcalls-api-webhooks.pdf?v=2026-11-11` и встроенной документации кабинета.
2. В CRM → CRMCalls → «CRMCalls → Новые заказы» выберите основной сценарий, его результат и соответствия операторов. Для М и Ж добавьте второй сценарий кнопкой «Добавить сценарий» и выберите его результат «СМ СРМ». Каждая пара проверяется отдельно; ID результатов между сценариями не взаимозаменяемы. Существующая настройка одного сценария сохраняется. При первом сохранении сервер создаёт отдельный случайный секрет и показывает его один раз. В БД хранится SHA-256; секрет не входит в репозиторий, URL, ответы чтения и журналы. Сохраните секрет в защищённом хранилище. Потеря секрета до настройки требует отдельной ротации; не включайте неподтверждённое подключение.
3. В каждом выбранном сценарии CRMCalls добавьте Webhook **только для «СМ СРМ»**, конечный HTTPS URL `https://crm.smanalytics.ru/api/crmcalls-incoming`, заголовок `Authorization: Bearer <секрет>`. Не используйте существующий API-ключ CRMCalls как секрет приёмника.
4. Сопоставьте следующие источники с JSON-ключами того же имени (точка создаёт вложенный объект):
   - `call.id`, `call.status`, `call.comment`;
   - `scenario.id`, `result.id`, `result.name`;
   - `user.id`, `user.name`;
   - `contact.id`, `contact.full_name`, `contact.phone`, `contact.phones`, `contact.city`, `contact.address`.
5. `event`, `event_id`, `occurred_at` и `Idempotency-Key` добавляет CRMCalls. Заголовок должен совпадать с `event_id`. Приёмник ограничивает тело 64 КиБ; настройки выбирают только перечисленные поля.
6. Включите приём и сохраните сценарий. Проверьте согласованный тестовый звонок с первым результатом «СМ СРМ»: webhook должен получить 200, журнал CRM — статус «Создана карточка», карточка — «Новый», пустая корзина и правильный оператор. Локальные тесты не подтверждают настройку провайдера. Звонки не выполняются при сохранении настроек CRM.

**Особенность CRMCalls:** webhook отправляется только при первом сохранении результата. Изменение ранее сохранённого результата не вызывает повторное событие. Если оператор сначала выбрал другой результат, последующая замена на «СМ СРМ» не передаст карточку автоматически. Не обещать пользователям передачу при любом редактировании результата.

## Надёжность и конфликты

Тело события сохраняется до HTTP200 в `crmcalls_incoming`, с постоянной дедупликацией по `call.id` и `event_id`. Повтор не заменяет первый снимок контакта. При отключённом приёме/переполнении возвращается 503; неверный секрет — 403. Другой сценарий/результат и события до начальной даты подключения игнорируются. Секрет проверяется сравнением одинаковых SHA-256, не как браузерная сессия.

Обработка выполняется сразу после сохранения без внешних API-запросов. Временные ошибки обработки повторяются существующим `sync-base` (50 за проход, сначала давно проверявшиеся), а также кнопкой «Повторить обработку». Служба не создаётся и не включается автоматически. Отправка из CRM в CRMCalls и приём имеют отдельные настройки.

Найденный клиент сопоставляется по нормализованным телефонам. Разные клиенты на нескольких телефонах, архив, чужой владелец, действующий заказ, ЧС/ПВ и неизвестный/отключённый оператор оставляют запись на сверке. Такие записи видны администратору с причиной; автоматического обхода ограничений нет. После штатного разрешения конфликта обработку можно повторить кнопкой. Фоновый исполнитель не повторяет записи на ручной сверке, даже если прежний конфликт позднее исчезнет. Создание карточки, закрепление клиента, запись журнала и завершение передачи выполняются одной транзакцией с проверкой версии клиента, оператора, настроек и существующих заказов.

В существующем клиенте сохраняются имя, телефоны и заполненный адрес; отличающийся адрес CRMCalls попадает в комментарий для сверки. Новый клиент получает стандартные поля и дополнительные телефоны. Заказ получает номер общего счётчика SM; источник CRMCalls сохранён в журнале и таблице передач. ФИО и комментарий передаются как текст.

## Публикация и откат

Следовать `docs/deployment.md`: отдельная ветка/PR, успешные проверки, main-релиз и подтверждение установленной версии. Новая таблица и настройка совместимы со старыми версиями. Bundler существующего `sync-base` включает импорт автоматически. Не менять файлы production runtime или телефонию вручную.

До отката выключить действие webhook у провайдера и приём в CRM. Сохранить `crmcalls_incoming`, настройку `crmcalls-incoming-config` и общий журнал номеров; не удалять созданные клиенты/заказы и не очищать дедупликацию. Возврат старой версии не отменяет уже принятые карточки.

Проверки: `node --experimental-strip-types tests/crmcalls-incoming.mjs`, TypeScript и штатный `CRM build and release`. Синтетические тесты используют только временную SQLite в памяти.
