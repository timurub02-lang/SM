# Входящие 8-800 без LeadVertex — предрелиз ALE-42

Статус: первая отдельная версия для испытаний. Production не переключён. Ветка/PR
не должны объединяться в main ради испытаний: main автоматически публикуется в CRM.
Рабочие номера, данные, секреты, ЛВ и маршруты Asterisk этой разработкой не меняются.
Существующий стенд Oktell также не предназначен для перезаписи этим пакетом.

## Поведение

```text
Доверенный trunk МегаФон/МТТ
  -> AGI сохраняет событие в локальную SQLite (FULL + WAL)
  -> приветствие -> завершение вызова
Параллельно: отдельный worker -> HTTPS CRM -> атомарно журнал + задача «Входящие»
```

Сохранение выполняется до Answer/Playback. Сеть, ЛВ, выгрузка аудио и распознавание
не участвуют в AGI. Ошибка локального сохранения завершает вызов с cause 41 без
обещания перезвонить. Если абонент завершил звонок после сохранения, задача всё равно
доставляется. Звонок, который вообще не дошёл до dialplan, этот модуль увидеть не может.

Сценарий не требует нажатия 1. Это отдельный доверенный маршрут; прежние правила
screening неизвестных номеров на остальных входящих сохранены.

- Известный клиент: текущие правила CRM выбирают ответственного (включая выкуп/
  логистику и связь с заказом). Правила ope-who из ЛВ не копируются.
- Нет подходящего ответственного/неизвестный клиент: задача попадает в существующую
  общую очередь руководителей и администратора. Клиент/заказ автоматически не создаётся.
- Новый звонок с того же телефона дополняет открытую задачу и увеличивает callCount.
  Ручное назначение открытой задачи сохраняется. После закрытия создаётся новая.
- Повторная доставка того же события не увеличивает счётчик. Старый повтор после
  закрытия возвращает первоначальную квитанцию, не открывает новую задачу.
- Заблокированный в CRM номер: журнал `blocked`, задачи нет.
- Скрытый/неподдерживаемый номер или конфликт клиентской привязки открытой задачи:
  журнал `review`, задачи нет. Первая версия работает с российскими +7 номерами;
  международные номера требуют отдельного решения. Повторный звонок в открытую
  спам-задачу также требует разбора.
- Источник задачи отображается как «МегаФон · 8-800» / «МТТ · 8-800». При объединении
  разных источников — «Входящие · несколько источников». Все DID остаются в событиях.

## Контракт и гарантия доставки

`POST /api/telephony/incoming-800`, отдельный заголовок `x-crm-incoming-key`.

```json
{"v":1,"node":"pbx-lab-800","callId":"1234567890.1","route":"megafon","phone":"+79990000001","calledNumber":"+78000000001","at":"2026-11-23T12:00:00.000Z"}
```

Все номера в этом документе и example-конфиге — синтетические. Дополнительные поля
запрещены, тело максимум 4096 байт. `phone:""` означает неопределённый номер.
`at` — UTC, фиксируется при первом сохранении; повтор AGI сохраняет исходное время.
`callId` берётся из Asterisk `agi_uniqueid`; node должен быть постоянным и уникальным
для инсталляции АТС. При клонировании/восстановлении АТС с риском повторного uniqueid
нужен новый node и согласованное разрешение на стороне CRM. Очередь от старого node
сначала доставить отдельно; нельзя менять поля уже сохранённых событий.

Идентификатор — `AST800-` + первые 32 hex SHA256(`node:callId`). CRM одной транзакцией
сохраняет событие и изменение задачи. Тот же ID с иным содержимым получает 409.
Квитанция содержит `ok,eventId,disposition,requestId,reason`.

Доставка выполняется как минимум один раз, бизнес-эффект дедуплицируется. При обрыве
после фиксации CRM worker повторит событие и получит ту же квитанцию. Локальная lease
30 секунд защищает очередь от конкурирующих workers; после смерти процесса задание
снова доступно. Таймаут HTTP 3 секунды, опрос 0,5 секунды, backoff 1–60 секунд без
лимита попыток. Даже при одновременной доставке после истечения lease CRM не создаст дубль.

`400/409/413` переводят событие в `quarantine`, остальные ошибки (включая 403/404,
неверную квитанцию, redirect, таймаут) оставляют `pending`. Redirect не переносит ключ.
Принятые/заблокированные/review/quarantine события сохраняются локально; автоматического
удаления нет. Принятые события CRM также сохраняются независимо от удаления карточки.
Утрата диска АТС до доставки не покрывается локальной SQLite: резервирование/внешняя
копия и операторский журнал нужны в эксплуатационной версии.

## Изолированная настройка

Приёмник по умолчанию отключён (404 до обращения к БД). Только в отдельном тестовом
экземпляре CRM с пустой синтетической БД:

```text
CRM_INCOMING_800_ENABLED=1
CRM_INCOMING_800_NODE=pbx-lab-800
CRM_INCOMING_800_ROUTES={"megafon":"+78000000001","mtt":"+78000000002"}
CRM_INCOMING_800_KEY=<отдельный случайный секрет, минимум 32 байта>
```

Пакет CRM содержит endpoint; PBX-часть публикуется отдельно как artifact
`incoming-800-prerelease-<SHA>`. Ни пакет, ни unit не устанавливаются автоматически.
Значения в `scripts/pbx/crm-incoming-800.example.json` — шаблон, не готовый секрет.

Для будущего отдельного Asterisk-стенда: Python 3.10+, SQLite, учётная запись asterisk.
Скрипт устанавливается как `/usr/local/libexec/crm-incoming-800.py` (root,0755),
конфиг `/etc/asterisk/crm-incoming-800.json` (root:asterisk,0640), очередь
`/var/lib/sm-crm-incoming-800` (asterisk,0700). Unit создаёт StateDirectory при старте;
каталог должен существовать с этими правами и до первого AGI.
В конфиге node/routes/key должны совпадать с отдельной CRM. Только HTTPS; HTTP
разрешён скриптом исключительно для loopback автоматических тестов.

Dialplan из `crm-incoming-800.extensions.conf` — неактивный шаблон. Включать его и
направлять в него только отдельный доверенный тестовый trunk после проверки endpoint
identify/auth и отсутствия доступа из публичного SIP-контекста. Нельзя принимать route
или DID от произвольного абонента: маршрут задаётся фиксированным контекстом trunk.
Аудио `custom/crm800-greeting` установить отдельно из утверждённого приветствия,
проверить формат/наличие/проигрывание. Файл аудио в репозиторий не включён.

## Диагностика и разбор

Локальный безопасный отчёт без телефонов/секретов:

```sh
python3 /usr/local/libexec/crm-incoming-800.py status
```

Поля: counts по состояниям, oldestPendingSeconds и агрегированные коды ошибок.
Состояние `review`/`quarantine` требует разбора администратором, а не считается успешно
поставленной задачей. В первой версии отдельного экрана разбора нет: ограниченный
доступ к `queue.receipt` и `incoming_800_events` позволяет найти eventId/requestId/reason.
`payload` содержит телефон — его не выводить в общие логи/задачи Linear.
Не менять исходный payload или удалять квитанции ради повтора. Исправление бизнес-
конфликта и ручное создание/привязка задачи должны фиксироваться администратором;
автоматический повтор уже подтверждённого review не перераспределит задачу.

До эксплуатации добавить оповещения: worker остановлен, pending старше порога,
quarantine/review, свободный диск и отсутствие SIP-регистрации. Обычный health-check
CRM не доказывает приём звонков оператором. Автовосстановление регистрации не входит
в этот первый срез. Текущая поломка регистрации 8-800 — отдельная причина потерь до AGI.

## Проверки и границы предрелиза

```sh
node --experimental-strip-types tests/incoming-800.mjs
python3 tests/incoming-800-queue.py
# После изолированной сборки CRM_RUNTIME=miran:
node --experimental-strip-types tests/incoming-800-http.mjs
```

Тесты: отключённый endpoint/другой ключ/неверный источник, конкурентные дубли,
повторные звонки, закрытие, привязка известного клиента, блокировка/скрытый номер,
откат транзакции, прежнее screening, сохранность при перезапуске, потеря ACK,
HTTP-сбои/redirect/неверная квитанция, истечение lease, карантин, реальный HTTP
standalone CRM с Python AGI/worker. Все данные синтетические, внешних звонков нет.

До production остаются: настоящий Asterisk и оба оператора (приветствие, отмена до/
во время AGI, ранний отбой, авария диска), нагрузка и p95 от входящего события до задачи
с целевым ≤3 с при доступной CRM, мониторинг и процедура разбора. Локальные миллисекунды
доставки не являются измерением SLA на реальной АТС. Публичный TLS/Nginx также проверить
на отдельном стенде.

Переключение после отдельного решения: согласовать момент отсечения для каждого DID,
остановить новые LV-события именно этого маршрута, доставить/сверить хвост LV-очереди
и импорта, затем включить новый маршрут. Нельзя одновременно создавать через ЛВ и
новый endpoint: у них разные ID и автоматической межсистемной дедупликации нет.
Откат: прекратить новые события нового маршрута, сверить и сохранить его очередь/
квитанции, вернуть прежний маршрут по согласованному времени; уже созданные задачи
не удалять. Не проигрывать один и тот же хвост через два приёмника.
