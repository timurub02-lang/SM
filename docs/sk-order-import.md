# Скорозвон → заказы CRM

Основной быстрый путь — событие `call_result` на `POST /api/sk-order-events`, постоянная очередь SQLite и отдельный `scripts/sync-sk-events.mjs`. HTTP подтверждает `202` только после записи события; внешний API и создание заказа выполняются вне веб-процесса. Исполнитель проверяет очередь раз в секунду, до пяти событий за проход, сверяет звонок и контакт через API и применяет прежние правила `acceptSkOrder`. Событие не позволяет обойти завершение звонка, права или бизнес-конфликт.

Страховочный сборщик `scripts/sync-sk-orders.mjs` продолжает работать раз в минуту с прежним перекрытием отчёта 24 часа. Входящие LeadVertex вынесены в `scripts/sync-lv-incoming.mjs` и собственный минутный таймер: задержка LV и длинный отчёт SK не останавливают обработчик событий. Если webhook ещё не настроен, остаётся прежняя минутная задержка; публикация кода сама по себе не подключает webhook.

Контракт проверен 12.11.2026 по [официальной документации Скорозвона](https://app.skorozvon.ru/static/skorozvon/docs/SkorozvonAPI.pdf), раздел Webhooks: `call_result` отправляется при сохранении результата, первая попытка сразу; `Idempotency-Key` повторяется при повторной доставке. `form_response` использовать нельзя: он может предшествовать окончательному результату. Провайдер разрешает настроить заголовок Authorization. Для REST указан лимит 10 запросов/с, для отчётов — один одновременно исполняемый запрос аккаунта на путь.

Нужны отдельный случайный секрет `CRM_SK_WEBHOOK_KEY` (не менее 32 символов, рекомендуется 32 случайных байта в hex), HTTPS URL и `Authorization: Bearer <секрет>` в настройке webhook Скорозвона. Секрет только в `/etc/sm-crm.env` и настройке провайдера, никогда в URL, репозитории или логах. Тело JSON ограничено 64 КиБ, сохраняются только call ID, result ID, комментарий и ключ события; контакт и сотрудник берутся заново из доверенного API. Дубли одного звонка не меняют первый снимок. При отключённом импорте или заполнении очереди из 10000 необработанных событий сервер возвращает 503 для повтора, не подтверждает потерю.

API-запросы импорта, событий и активности используют общий бюджет SQLite: 4 старта/с; OAuth тоже учитывается. Отдельная блокировка ограничивает только одновременные `calls_total` и освобождается после получения тела или ошибки; HTTP timeout ≤ 30 с, срок блокировки 35 с. Ответ 429 сохраняет общую паузу с Retry-After; активность сохраняет свои ограниченные повторы. Остальные действующие интеграции SK пока используют свой темп запросов — общий лимит аккаунта не подтверждён боевым замером.

Очередь сохраняется при остановке и перезапуске; одно событие закрепляется за исполнителем на 120 с. При ошибке повтор через 1–300 с, после 429 — по общей паузе. Подтверждённые события удаляются из очереди через 24 часа, постоянная дедупликация остаётся в `sk_order_transfers`. Pending по бизнес-правилам считается обработанной передачей, не ошибкой доставки. Неизвестный телефон и незавершённый звонок остаются в очереди. В процессе обработки событий справочник SK и token кэшируются до 30 с; смена реквизитов или ошибка сбрасывает кэш. Доступ оператора CRM проверяется заново при создании.

Это убирает наше минутное ожидание для полученного события, но не даёт обещания нулевой задержки: реальная доставка SK, его API, ограничения, очередь и обновление интерфейса измеряются отдельно. Всплеск 47 одновременных новых звонков требует ≥ 94 API-запросов, поэтому один темп 4/с занимает около 23.5 с до обработки всего всплеска. Обычный одиночный результат не ждёт эту очередь, когда её нет.

Настройка в `settings`, id `sk-order-import`: `{enabled:true,enabledAt:<ISO>,resultIds:[50000520226]}`. Этот ID соответствует «СМ СРМ» сценария 50000003318. До включения проверить ID через API. Старые звонки до enabledAt не импортируются. Отчёт проверяется с перекрытием 24 часа от последней успешной проверки для отложенного сохранения результатов; изменения результатов более старых звонков после этого окна не подхватываются. Для них потребуется отдельная согласованная обработка.

Автор определяется по уникальному ФИО пользователя СК и точному полю `skLogin` («ФИО в Скорозвоне») в CRM. Регистр и повторные пробелы не учитываются, приставки сохраняются. Неоднозначное или отсутствующее соответствие остаётся в `sk_order_transfers`, без заказа. Идентификатор звонка — ключ повторной передачи. Данные первого получения сохраняются; повторы не заменяют их.

Новый заказ создаётся в «Оформлении» с пустой корзиной до следующего этапа сопоставления полей. Стандартные имя, телефон, город, адрес и комментарий берутся из API. Существующий адрес не перезаписывается; адрес из СК сохраняется в комментарии заказа для сверки. Клиент закрепляется за оператором и переходит на «К», с сохранением обратного листа и штатной логикой удержания.

Чужой владелец, действующий заказ или лист ЧС/ПВ требуют решения. Серые заявки отображаются в разделе «Заказы» у отправителя, администратора и руководителя текущего владельца (для свободного клиента — руководителя отправителя). Разрешение создаёт заказ и закрепляет клиента за отправителем, отклонение не меняет клиента. ЧС/ПВ разрешает только администратор. Ожидающая заявка не запускает срок оформления; он начинается при создании заказа.

`sk-order-health` хранит результат последнего запуска, ошибки видны администратору в разделе «Заказы». Установка systemd unit-файлов из `scripts/systemd/` выполняется после публикации и резервной копии. Секреты Скорозвона читаются из существующей настройки и не входят в исходники.
