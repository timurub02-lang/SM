# Развёртывание CRM на Миране

Исходники: `https://github.com/timurub02-lang/SM`, ветка `main`.
VM: `crm`, адрес `10.20.0.10`, домен `https://crm.smanalytics.ru`.

Серверная версия собирается командой `CRM_RUNTIME=miran npx next build --webpack`.
Используется Node.js 24 и встроенный SQLite. Сборка Next.js заменяет модуль
`cloudflare:workers` локальным адаптером; локальная версия Sites продолжает работать с D1.

Данные находятся отдельно от кода: `/var/lib/sm-crm/crm.sqlite`.
`CRM_DATABASE_PATH=... node scripts/init-sqlite.mjs` создаёт схему пустой базы
или проверяет существующую. Нельзя копировать работающую SQLite-базу обычным
копированием: используйте SQLite backup API, который учитывает WAL.

Приложение слушает только `127.0.0.1:3000`. Nginx завершает HTTPS и заменяет
`X-Real-IP`; личный вход и права проверяет приложение.
Переменные находятся в `/etc/sm-crm.env`. Эти файлы и базы никогда не добавляются в Git.

Обновления: изменить проект → проверить типы, тест SQLite и сборку → commit/push
в GitHub → получить код в новый каталог релиза `/srv/crm/releases/<commit>` →
`npm ci` → собрать → скопировать `public` и `.next/static` в `.next/standalone` →
сохранить резервную копию базы → переключить `/srv/crm/current` → перезапустить
только `sm-crm.service` → проверить сайт и API. Предыдущий релиз сохранять для отката.
Простое обновление кода не должно заново инициализировать или очищать базу.

Проверки: `npx tsc --noEmit`, `node --experimental-strip-types tests/sqlite.mjs`.
Без сеанса `/` перенаправляет на `/login`, `/api/crm` отвечает 401; после входа оба — 200.
Проверять также запрет неподходящего Origin и подмены заголовков пользователя.

## Персональный вход

На Миране `/login` принимает логин из карточки сотрудника и пароль.
Администратор управляет доступом в «Команда»: задаёт/сбрасывает пароль
(12–128 символов), включает и отключает вход. Руководитель может управлять
только операторами своего отдела. Старые карточки без пароля не дают входа.
Пароли хешируются scrypt; cookie HttpOnly/Secure/SameSite=Strict содержит
случайный сеанс на 12 часов. В базе сохраняется только хеш токена.
Смена пароля, логина, роли, отдела и отключение доступа завершают сеансы.
Сервер проверяет сотрудника и его права; переданный клиентом actorId не даёт
права переключиться на другого сотрудника. Ответы CRM ограничены его данными.

Первичная подготовка: `CRM_DATABASE_PATH=... node scripts/init-auth.mjs`.
Однократно `--bootstrap-admin` создаёт доступ существующему сотруднику `admin`,
читая пароль из stdin. Повторное выполнение не заменяет пароль.
После настройки nginx больше не использует общий Basic Auth и не передаёт
фиктивного пользователя: вход проверяет приложение. Nginx заменяет X-Real-IP
для ограничения перебора паролей. Локальный Sites-preview сохраняет прежний
режим просмотра; он не предназначен для публичного доступа сотрудников.

После standalone-сборки: `node --experimental-strip-types tests/auth-http.mjs`.
Проверка использует временную базу с искусственными данными, не рабочую CRM.

## Удаление сотрудников

В «Команда» → карточка сотрудника → «Удалить сотрудника» администратор может
удалить другого сотрудника любой роли, руководитель — оператора своего отдела.
Собственную учётную запись удалить нельзя. Перед подтверждением выбирается
передача всех закреплённых клиентов и их заказов (включая завершённые) другому
оператору того же отдела либо освобождение клиентов. Доступ получателя можно
настроить отдельно, он не обязан быть включён на момент передачи.

При освобождении активные заказы оставляют свободного клиента на «К»; выкупленные
без активных — сразу «ТК» без ожидания 35 дней; остальные возвращаются на исходный
лист. Без заказов используется лист возврата, по умолчанию «Т1». Статусы заказов
не меняются. Обычные правила срока закрепления продолжают действовать при передаче.

Клиенты и заказы не удаляются. История переназначения записывается в события,
профиль удалённого сотрудника сохраняется в settings как deleted-employee-<id>.
Сеансы и возможность входа удаляются в той же транзакции. Если версии данных
успели измениться или запись не удалась, операция не применяется частично.
Проверки: tests/employee-removal.mjs и tests/auth-http.mjs на временной базе.

## Скорозвон: только соединение

«Настройки» → «Скорозвон» доступны администратору. Проверка получает OAuth-токен
и выполняет GET /api/v2/users?length=1. Реквизиты сохраняются в settings/skorozvon
только после успешной проверки. Ключи не возвращаются в браузер; пустые поля
при повторной проверке используют сохранённые значения. Токен проверки не хранится.
Обмен клиентами, проекты, звонки, webhooks и фоновые задания пока не включены.
Официальная документация: https://app.skorozvon.ru/static/skorozvon/docs/SkorozvonAPI.pdf

## Фоновое обновление отправлений СДЭК

Установить `scripts/sm-crm-cdek-shipments.service` и `.timer` в
`/etc/systemd/system/`, выполнить `systemctl daemon-reload` и
`systemctl enable --now sm-crm-cdek-shipments.timer`.
Таймер раз в минуту запускает `scripts/sync-cdek-shipments.mjs` от crmadmin
с `/etc/sm-crm.env` и рабочей базой. Новые запуски не пересекаются с ещё
выполняющимся oneshot. Обрабатывается до 200 активных отправлений, по четыре
запроса одновременно; самые давно проверенные идут первыми. Для удаления
отправлений продолжает работать отдельный `sm-crm-cdek-deletions.timer`.
Состояние последнего прохода записывается в settings `cdek-sync-health`.
Проверка без рабочего API: `node --experimental-strip-types tests/cdek-background.mjs`.
